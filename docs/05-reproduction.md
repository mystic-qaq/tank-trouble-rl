# 05 · Reproduction

The repository is a **research snapshot**: the game and arena run anywhere with Node and a browser; the learning pipeline assumes a Linux GPU host and a frozen demonstration corpus that is not shipped (about 80 GB). This note explains what runs out of the box, what needs the corpus, and which numbers to expect.

---

## 1. What you need

| Component | Version / note |
|---|---|
| Browser | Any modern Chromium/Firefox for the game and spectator page |
| Node.js | 22.x (uses `vm.SourceTextModule`; run with `--experimental-vm-modules`) |
| Python | 3.11+ for the learning code |
| PyTorch | 2.11.0+cu128 (see `policy/rl/requirements.txt`) |
| numpy / pytest / tensorboard | same requirements file |
| GPU | Optional for the arena; 1–2 cards for training. The original runs deliberately capped at 2 |
| Disk | ~80 GB for the corpus, plus a few GB for checkpoints and TensorBoard |

```bash
python -m venv .venv
. .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r policy/rl/requirements.txt
```

## 2. Play the game

No build step:

```bash
python -m http.server 8000
# http://localhost:8000/
```

Or double-click `index.html`. Controls: P1 `WASD + Space`, P2 arrow keys + `Enter`; `Esc` pauses, `M` mutes. The main menu also has **AI 观战 (Arena)**, a pure spectator mode.

The game is asset-free: Canvas primitives for rendering, WebAudio for sound.

---

## 3. Run the agent arena

```bash
# 208 balanced rounds, 8 agents, two maps, seat rotation
node --experimental-vm-modules arena/run.mjs --rounds 208 --seed 20260101 --jobs 8

# A smaller sanity check
node --experimental-vm-modules arena/run.mjs --rounds 16 --players gpt,hy --jobs 2

# Physics and schedule regressions
node arena/regression.mjs

# Frozen source manifest (7 policies, 74 files)
node policy/verify-frozen.mjs
```

Audits:

```bash
node --experimental-vm-modules arena/audit.mjs
node --experimental-vm-modules arena/steer-audit.mjs
node --experimental-vm-modules arena/seat-check.mjs
node --experimental-vm-modules arena/head2head.mjs
```

Browser spectator: open `arena/index.html`. It works from `file://`; the two ESM policies are loaded from `arena/vendor/*.classic.js`, generated by `node arena/build-vendor.mjs`.

The ONNX presets (`v2-win`, `v2-frag`, `v7-distill1`) are in `arena/models/`. The browser fetches the model card, verifies `onnx_sha256`, and runs inference through ONNX Runtime Web.

## 5. Training pipeline

### 5.1 Data layout

The collectors write a directory per corpus split:

```text
data/
├── multi/
│   ├── manifest.json
│   ├── status.json
│   └── <world>/<trajectory>.npy
└── skills/
    ├── manifest.json
    └── ...
```

Each frame is a float32 vector; the multi corpus uses the 1,966-D schema for V1–V7. V8 uses a new 608 + 346 schema and a separate collector.

A **data receipt** is a JSON file mapping every `.npy` to its SHA-256 and shape. It is produced by the collector and checked by G0.

### 5.2 G0 — contract audit

```bash
python -m policy.rl.v4.pipeline --prepare-only \
  --out runs/g0-$(date +%s) \
  --data data/multi data/skills \
  --device cpu --seconds 1200
```

G0 verifies:

- source digest over `js/`, `arena/`, `policy/` (`.py`, `.mjs`, `.js`, `.json`);
- observation schema and action-space contract;
- every data file against the receipt;
- that the checkpoint architecture matches the code.

It writes `contracts.json` / `g0.json` and fails closed. **Any edit to a hashed source file requires a new G0 and a new output directory.**

### 5.3 BC + PPO (V5 code)

```bash
# BC bootstrap only
python -m policy.rl.v4.train --help

# PPO from a BC checkpoint
python -m policy.rl.v4.optimize \
  --config policy/rl/v4/config.json \
  --data data/multi data/skills \
  --data-receipt data/receipt.json \
  --out runs/ppo-$(date +%s) \
  --objective win --device cuda:0 \
  --seconds 5400 --acceptance-seconds 1200 \
  --init runs/bc/best.pt --phase fork
```

For a shared-then-fork run, use `--phase shared --skip-acceptance` for the shared stage, then `--phase fork --init shared/best.pt` for each objective. The exact V6 scripts are in [`research/v6/`](../research/v6/), including the quality gate that refuses to fork from a bad checkpoint.

### 5.4 V8

```bash
python -m policy.rl.v8.collect --help
python -m policy.rl.v8.train --help
python -m policy.rl.v8.rl --help
python -m policy.rl.v8.evaluate --help
python -m policy.rl.v8.export --help
```

`policy/rl/v8/run_stage1.sh` is the staged script used for the V8 attempt (collection wait → phase A → phase B). It is a record of the run, not a turnkey installer.

## 6. Reading the artifacts

| Artifact | Meaning |
|---|---|
| `status.json` | Last iteration: score, fitness, kills, suicides, KL, frames, timing, `certified`, `reverted` |
| `result.json` | Final history and status after the run |
| `acceptance.json` | Independent dev gate result (student, teacher, required, suicides, accepted) |
| `shared-gate.json` | V6B handoff: quality checks on the shared checkpoint, `fork2_suppressed` |
| `manifest.json` | Checkpoint provenance: architecture, iteration, score, dev probe, stop reason |
| TensorBoard `tb/` | Per-iteration scalars (score, kills, suicides, KL, frames, collect/update seconds) |

`research/results.csv` is the compact cross-version table. It is generated from the JSON/log files, not typed by hand.

## 7. Known pitfalls

1. **Do not train from NFS.** The original host had a hard `nfs4` mount that hung for six hours and left 60 processes in `D` state. Copy the corpus to local disk; keep checkpoints and logs local too.
2. **Do not use `DataParallel` for a 2M-parameter model.** It splits a small batch into tiny slices and adds synchronization. One GPU with a larger batch was ~7× faster in samples/s.
3. **The GPU is not the bottleneck.** The JS engine runs on CPU; a rollout can take 60–77 s while the PPO update takes 5–11 s. Optimise worker count and data locality before model size.
4. **A "finished" run is not a "good" run.** The first V6 gate only checked that the process exited and the checkpoint loaded; it passed a checkpoint with −0.44 net kills to the forks. Use a quality gate (net kills, suicides, iteration count) and fail closed.
5. **The KL trust region is not optional.** Teacher-guided KL was rejected on every iteration in two A/B runs. If you re-enable it, log the exact mean KL and roll back; do not silently clip.
6. **Never tune the decoder after training.** The acceptance sampled decoder must be the training distribution. Changing temperature to pass the gate invalidates the result.
7. **Per-n evaluation matters.** V7 wins 62.5% of 2-player rounds and 0% at n=6. An aggregate number hides this; always report the per-n table.

## 8. Expected numbers

If you rerun the frozen development split with the published V7 weights, expect approximately:

| Metric | Value |
|---|---:|
| Greedy win rate | 16.4% |
| Sampled win rate | 9.5% |
| Net kills (greedy) | +0.43 |
| Suicides (greedy) | 0.183 |
| Draws | 24.3% |
| Teacher (HY) win rate | 30.2% |
| Acceptance gate | 21.1% |

Small differences are expected from worker count, float nondeterminism in the engine, and the exact `dev_blocks`; the conclusion (below the gate) is robust.

## 9. What is intentionally missing

- The 80 GB demonstration corpus (rebuild with the collectors).
- Training checkpoints (`.pt`), except the three ONNX models used by the browser arena.
- Raw rollout dumps and TensorBoard event files from the long runs.
- Cluster-specific scripts with usernames and absolute paths; `research/v6/` contains normalised copies of the important ones.

The repository is meant to be **auditable and rerunnable in principle**, not a one-click reproduction of a multi-day GPU run.
