# 两个可训练策略的实施方案

日期：2026-11-06。状态：首版环境、教师采集、BC/PPO 与开发验证已实现，正在启动 Server3090 初始实验。

目标是训练两个独立模型：`rl_win` 在约定的随机对局分布中提高回合胜率，`rl_frag` 提高每回合净击杀。分别以 HY、GPT 为主要基线；通过验收后替换内置 Bot 和 minimax。现有七份策略保持原样，作为教师、对手和回归基线。

## 1. 当前基础与缺口

- `policy/rl/` 已加入首版实现，运行方式见 README.md。
- `arena/arena.mjs` 有真实 JS 引擎、隔离沙箱、确定性种子、2–8 人配置、出生布局记录和席位配平。
- `arena/sim/` 有名单抽样、人数分层、逐局记录及布局簇统计，可以扩展为模型验证器。
- `playRound()` 保留整局评估功能；训练新增 `env.mjs` 和批量桥接的逐帧接口。
- 现有汇总结果不能直接训练行为克隆；需要重新记录逐步观测和教师动作。旧的随机种子和名单可以复用。
- 本机实际查询到 RTX 4060 Laptop GPU，显存约 8 GiB，适合本方案的小网络。模拟吞吐须另外测量。

## 2. 先固定目标和评估分布

设随机场景 c 包含人数、地图、出生布局、朝向、名单和随机流。D 是预先固定的场景分布。

| 模型 | 主要目标 | 基线 | 不混入主要指标的项目 |
| --- | --- | --- | --- |
| rl_win | E_D[本回合获胜指示值] | HY | 生存时间、击杀数量、第二名次数 |
| rl_frag | E_D[击杀他人次数 − 自毁次数] | GPT | 击杀/分钟、被他人击杀次数、回合胜率 |

第一版采用 N=2…8 各占 1/7，人数内地图 A/B 各半，名单从固定对手池抽取，出生点完整轮转。若实际游戏的人数分布不同，再增加一套按实际出场频率加权的成绩；训练与验收都记录其权重。

原始胜率和净击杀都按人数单独报告，跨人数汇总使用固定权重。不同人数可获得的击杀上限不同，不根据临时样本量直接合并排名。胜率分母包含平局，不改成仅在分出胜负的局中计算。

用户已确定正式游戏、Arena 和训练均采用 60 秒时限，超时平局；由共用引擎统一判定。旧 60 秒统计只作历史参考，基线须在 60 秒规则下重测。

## 3. 环境接口与执行边界

Python/PyTorch 批量产生动作，常驻 Node 环境运行 JS 真实引擎：

    reset(config, seed) -> observation, info
    step(action) -> observation, reward, terminated, truncated, info

reset 配置包括 learner 槽位、每个槽位的 policyId/模型版本、地图种子、出生种子、策略随机种子以及训练目标。step 默认推进一个 1/60 秒物理帧。训练阶段跳过开场和结算动画。

第一版只训练每个环境中的一个被控坦克，其他坦克使用冻结策略或冻结模型快照，避免同时更新所有对手。环境进程跨 step 常驻，每局仍重新隔离策略状态，不每帧重建 VM 或启动进程。

身份分为独立的 `agentId/seat` 与 `policyId`。这允许新策略注册、历史模型、同一 policy 的多个副本；现有 `validateRoster` 的硬编码名单及禁止重复逻辑不能直接充当训练环境的身份系统。

以下内容必须一致：

- 训练、评估、浏览器使用同一引擎和观测定义；不重新用 Python 编写近似物理。
- 默认模型和固定策略均按 60 Hz 决策。只有在单独验证后才考虑降低模型决策频率。
- 动作同样受游戏的速度、转向、冷却、存弹上限约束。
- 不向模型输入策略名称、对手私有缓存、未来动作、未来随机数等额外信息。
- 固定 seed 与动作序列可逐帧重放；种子分出出生、对手抽样、探索和环境随机流。
- 60 秒若是定义中的比赛规则，则到时是终止，观测提供剩余时间；仅为采样而切断 rollout 则不是比赛终止，需要用末状态价值接续估计。

特别注意：被控坦克死亡后，游戏中其子弹还可能击杀对手。净击杀模型必须继续结算到回合真正结束；死亡后不再采样动作，屏蔽 actor loss，但保留末尾奖励与价值学习。不能因死亡立刻 reset。rollout 切分边界也必须保留这条奖励链。

## 4. 输入、模型和动作

第一版采用结构化状态，避免从截图学习视觉。

| 输入 | 内容 |
| --- | --- |
| 自身 | 位置、朝向 sin/cos、速度、射击冷却、存活状态、自己在场子弹数 |
| 地图 | 水平/垂直墙边标志及边界；使用固定维度墙网格编码 |
| 对手 | 最多 7 个；相对位置、朝向、速度、公开冷却、存活状态和子弹数 |
| 子弹 | 最多 40 发；相对位置、速度方向、归属、剩余寿命、反弹数及必要的自伤宽限状态 |
| 全局 | 初始人数、当前存活数、剩余时间、上一动作 |

坐标归一化；实体槽位有有效性 mask，不能把填充的全零当作真实坦克或子弹。对手与子弹采用共享小 MLP 编码，再做带 mask 的池化；地图单独编码后与自身状态拼接。先采用约 10–50 万参数的前馈 actor/critic，256 维左右主干；出现明确的历史信息不足时才加 GRU。

保留全部 40 发子弹，不只保留最近几发。远处的反弹弹也可能构成威胁。训练可以使用水平/垂直镜像及 180° 旋转增强，但必须同步变换地图、位置、角度、速度和转向标签；16×10 的矩形地图不能直接当作 90° 旋转对称。

动作分为三个输出头：

- drive：后退 / 停止 / 前进，三分类；
- steer：[-1, 1] 连续值，训练时使用有正确概率密度变换的有界分布；
- shoot：是否开火，Bernoulli。

连续 steer 用于保留教师策略的小数精确转向。推理时确定性或随机采样规则固定并记录，不在模型比较时临时换规则。冷却期间可以屏蔽无效开火动作，但训练、导出、评估必须一致。

两个模型共用实现和数据格式，独立维护权重、优化器、奖励、检查点和模型选择规则。

## 5. 奖励设计：与真正目标保持一致

### rl_win

核心奖励只在结果确定时给出：获胜 +1；失利、同归于尽和超时均为 0。

不能长期使用“每活一秒加分”，否则可能学会拖到超时。也不直接采用胜 +1、败 −1、平 0，因为那优化的是胜率减败率，会改变对平局的偏好。击杀奖励、死亡惩罚和靠近敌人奖励也不作为最终阶段的固定附加项。

为了缓解稀疏奖励，首先使用 HY 的行为克隆。必要时可以研究有界势函数奖励 F=γΦ(s')−Φ(s)，但所有真正终止状态的势函数必须正确处理，并固定到相同目标与折扣约定；默认先不开启。简单“躲开一次子弹加分”可能被循环刷分，不能等同于保留目标的势函数塑形。

### rl_frag

逐帧核心奖励：

    reward = 新增击杀他人次数 − 新增自毁次数

整局累计奖励与游戏净击杀严格一致。被他人击杀不另扣一分；不能把目标悄悄改成“击杀 − 所有死亡”。不额外奖励射击次数、命中预测、造成威胁或获胜，也不以击杀/分钟替代每局净击杀。

第一版为有限回合任务，PPO 从 γ=1 开始，使优化的回报口径与未折扣指标一致；GAE λ 在 0.97–0.99 附近进行小规模验证。若后续为稳定性使用 γ<1，须承认它偏向更早奖励，并通过未折扣的真实指标选择和验收模型。

## 6. 学习顺序

### A. 教师初始化

分别采集 HY 和 GPT 的 (观测, 动作) 数据。第一批可从每位教师 20–100 万条状态动作样本开始，覆盖不同人数、地图、出生布局、冷却状态和子弹密度；按完整回合切分数据集。

drive 和 shoot 用分类损失，steer 用回归或相应分布损失。不要将多个教师在同一状态下冲突的动作简单求平均。复用同一编码实现，两个模型分别初始化。

教师在自己的轨迹上动作拟合得好，并不保证学生进入不同状态后表现好。验收必须让学生实际运行；出现偏航时，在学生访问的状态上查询原教师补充标签，再训练。少量射击样本需要分层采样，避免学到“从不开火”。

### B. 单模型 PPO

先用冻结的原始策略训练。PPO 是本项目的起始算法，选择依据是工程复杂度与混合动作支持，不是保证它一定优于所有其他算法。

可尝试的首轮配置：

| 参数 | 起点 |
| --- | --- |
| 并行环境 | 16，再对照 8 / 32 的端到端吞吐 |
| 每环境 rollout | 256 帧，必要时延长 |
| 学习率 | 1e-4，后期衰减 |
| PPO clip | 0.2 |
| 每轮更新 | 4 个 epoch，结合近似 KL 监控 |
| minibatch | 512，按实际显存和批量调整 |
| value loss 系数 | 0.5 |
| 教师辅助损失 | 初期保留，随训练衰减至 0 |
| 探索熵 | 按动作头分别调尺度，避免连续头与离散头混用同一未经校准的权重 |

上述是调参起点，不能视作已验证的最优参数。每轮采样冻结一个明确模型版本，记录 old log-prob/value 后再更新；不能把异步旧模型的大量经验直接当作同一版 PPO 的 on-policy 数据。

早期可短暂增加简单场景比例，但尽快恢复完整的 N=2…8 和混合对手训练分布。不能只打内置 Bot，或只打教师本人。降低时限作为课程会改变任务，恢复目标时限后必须重新验证。

### C. 对手池与历史快照

有稳定提升后再引入历史版本，初始每个对手槽位的来源比例可用：

- 60%：原始八种冻结策略，保证 HY/GPT 和弱策略都存在；
- 30%：两个学习模型各阶段的冻结快照；
- 10%：经独立验证确有克制作用的困难对手或场景。

这是初始抽样比例，需要按结果调整。保持一定均匀抽样，不全打当前最难对手。对手在整局内冻结，快照在采样批次边界更新。保留早期版本、进攻型与防守型版本，避免只适应最新一个模型或形成轮流克制。

两个模型前期分开训练以便排错；后期互相提供冻结对手，不让它们只彼此对战。

## 7. 评估与替换条件

数据分三层：训练场景、开发验证场景、最终一次性测试场景。最终测试的出生种子与至少一部分名单组合不参与训练、调参或挑选检查点。已用来挑模型的场景属于验证集，不能继续声称是未见测试集。

现有代码只提供两张固定地图。第一轮对齐这两张图；若要声称对新地图也泛化，另设地图种子划分，不能只换出生点。最终测试集不因测试结果不好而反复补训练。

主要比较采用“相同背景下替换被测槽位”：

1. 固定人数、背景对手、地图、出生布局、席位和随机种子；
2. 一次由 rl_win 占被测位置，一次由 HY 占同一位置；rl_frag 与 GPT 同理；
3. 在完整出生轮转块内配对比较，再按预先固定的人数权重汇总；
4. 按布局及跨名单共享随机块整体 bootstrap，保留配对和跨名单关联，计算指标差值的置信区间。

若背景中包含同一个基线策略，允许多个 agentId 使用同一个 policyId，而不是为某个被测模型改变背景名单。也要补充模型与基线同场的成绩，检验直接交手，但不把两种实验口径混为一谈。

开发期每 50–100 万环境帧做一次较小评估，少数候选再做大评估。正式比较先用约 2,000–5,000 个配对场景起步，再按实际“差值”的簇方差与目标精度调整，不能固定宣称任何局数都足以证明 1 个百分点优势。

建议在训练前锁定以下替换门槛：

- rl_win：加权胜率比 HY 高至少 3 个百分点，且配对差值 95% CI 下界大于 0；
- rl_frag：加权净击杀/局比 GPT 高至少 0.10，且配对差值 95% CI 下界大于 0；
- 分人数、地图、出生区域和名单分层都报告；不要求每个桶都显著更强，但检查是否出现实质性退化；
- 最终候选至少经过三个独立训练种子的开发复现，再冻结候选进行最终测试；
- 两个新模型一起替换旧策略后，另做部署阵容回归，因为对手分布已经改变；
- 统计超时、自毁、策略异常与推理延迟。不能仅凭训练奖励上升替换。

3 个百分点和 0.10 是建议的产品提升门槛，不是已知能达成的结果；训练前可以调整，测试后不再为了过关降低标准。

## 8. “实战中持续进步”的运行方式

RL 模型可以持续学习，但不会每局或每次梯度更新都变强。第一阶段先用加速模拟积累大量真实引擎交互。

随后采用：当前正式版本进行对战 → 收集轨迹 → 后台候选版本继续训练 → 固定验证集验收 → 有改进才晋升 → 保留旧版本可回滚。

正式对战和排行榜评估期间冻结权重，至少整局不变。若从正式对局采集的历史数据不是当前采样策略产生，不可直接混进 PPO 更新；可以用于额外模仿/分析，或另行设计离策略学习流程。正式对局数量少时，仍以后台模拟为主要学习来源。

训练奖励可记录、候选可持续更新；对玩家显示的模型版本、评估版本必须可追溯。早期实验不要直接覆盖已有 Bot/minimax 入口，先注册新模型，达标后再设置替代关系。

## 9. 浏览器部署与资源预算

为了兼容当前同步 `TT.updateBot` 和双击 HTML 的使用方式，优先将小网络导出为本地 JS 权重与同步前向计算，所有输入归一化、池化 mask、激活函数和动作解码与 Python 对齐。这属于通用推理实现，不是重新编写规则策略。

若使用 ONNX Runtime 等异步推理路径，则必须在物理步前批量算好动作再推进游戏，不能把 Promise 当作 `TT.updateBot` 的动作返回值。导出后用固定观测集逐项比较 logits、连续转向和最终动作，再比较完整回合结果与速度。

预计显存不是第一版小模型的主要障碍；现有模拟文档的基准显示，固定对手的路径搜索/射线计算成本很高。训练代码完成后必须重新测端到端环境帧/秒、推理、通信和优化分别耗时。

实验预算分档：

- 接口验证：几千到几万环境帧，检查奖励与真实成绩逐局相等；
- 首次学习验证：每模型 100–300 万环境帧，证明超过自身 BC 初始化，而不是直接承诺超过 HY/GPT；
- 正式提升实验：每模型先规划 1,000 万帧，视曲线按阶段扩展至 3,000–5,000 万帧；
- 端到端耗时 = 所需环境帧 ÷ 实测环境帧/秒 + 独立评估耗时。一个环境帧是一个游戏世界推进 1/60 秒；不能把八个对手的调用次数也算成八倍训练样本。

若 100–300 万帧尚无学习迹象，先查观测、动作/概率密度、奖励归因、死亡后结算、终止语义和教师分布偏移，不直接盲目增加到上亿帧。

## 10. 建议文件与交付顺序

目标文件组织如下，当前实现与启动命令以 README.md 为准：

    policy/rl/
      PLAN.md
      env.mjs             # 真实引擎 reset / step / 事件奖励 / 快照
      bridge.mjs          # 常驻批量环境通信
      observation.mjs     # 统一观测规范
      collect.mjs         # HY / GPT 教师样本
      model.py            # 两模型共用的网络定义
      train_bc.py
      train_ppo.py
      evaluate.mjs        # 配对替换和分层验证
      export.py
      runtime.js          # 浏览器同步推理
      configs/
      checkpoints/        # 权重、优化器和随机状态
      exported/

第一批交付只做 env/观测/奖励和回归：确定性重放、两种奖励与逐局统计完全一致、死亡后子弹归因、终止与采样截断区分、2–8 人及重复策略槽位。通过后再做 BC → PPO → 对手池 → 大评估 → 浏览器替换，每一步都有独立可检查结果。
